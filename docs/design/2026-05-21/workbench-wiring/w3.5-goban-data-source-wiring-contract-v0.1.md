## 1. User Stories

1. As a Workbench user, I want the board to display stones from the actual game tree, not a hardcoded empty board.
2. As a Play mode user, I want clicking an empty point to place a stone through a single resolver -> executor -> documentStore path.
3. As a Recall mode user, I want clicking to submit my recall answer without writing to the game tree.
4. As an Analysis mode user, I want board clicks to route to the scratch edit executor so free exploration doesn't affect Attempt.userLine.
5. As a Container, I want board rendering to reactively reflect documentStore/overlayStore/settings changes via adapter subscription.
6. As a developer, I want Container to have zero hardcoded board/overlay/settings data.
7. As a developer, I want the workbench click path to never call sabaki.clickVertex.

## 2. Deliverables

1. **gobanDataAdapter** — subscribes to board/overlay/settings data sources, outputs GobanPropsInput snapshot + subscribe
2. **boardInteractionController** — unified click -> resolver -> executor routing
3. **Container rewrite** — subscribe to adapter + forward click, remove all hardcoded data

## 3. Data Flow (Render Read Path)

```
State sources:
  sabaki.state (gameTrees, gameIndex, treePosition, selectedTool, editWorkspace, settings)
  documentStore (formal tree, board, navigation)
  overlayStore (territoryEnabled, territoryCompareEnabled)
  analysisResultAdapter (normalized analysis per position)
  workbenchStore (activeTab with mode, playerConfig, activeAttemptId)
  trainingRuntimeStore (activeCheckpointId, correctionDraft, recallView)

gobanDataAdapter.subscribe(snapshot => ...)
  -> aggregates into GobanPropsInput snapshot
  -> notifies Container via callback

Container render:
  gobanDataAdapter.getSnapshot()
    -> GobanPropsInput
    -> projectGobanProps(input)
    -> GobanPropsOutput
    -> WorkbenchShell -> MainBoardStage -> Goban
```

## 4. Click Flow (Command Write Path)

```
Goban.handleVertexMouseUp
  -> MainBoardStage.props.onVertexClick(vertex, event)
  -> Container.onVertexClick(vertex, event)
  -> boardInteractionController.handleBoardClick({vertex, event, activeTab, settings, board})
  -> createBoardInteractionContext({...}) -> ResolverInput
  -> resolveBoardInteraction(resolverInput) -> BoardInteractionResult
  -> route by mutationContract:
       'playMove'     -> playInteractionExecutor -> documentStore.playMove
       'recallAnswer' -> recallInteractionExecutor -> recallService
       'scratchEdit'  -> scratchEditInteractionExecutor -> editWorkspace
       deferred       -> sabaki.clickVertex (migration seam)
       rejected/noop  -> no action
  -> executor performs write
  -> store/adapter update fires subscription
  -> gobanDataAdapter re-reads snapshot
  -> Container re-renders -> Goban shows updated state
```

## 6. gobanDataAdapter Specification

**File:** `src/modules/training/adapter/gobanDataAdapter.ts`

### Dependencies (injected)

```ts
type GobanDataAdapterDeps = {
  getSabakiState: () => SabakiStateSubset
  getDocumentStore: () => DocumentStoreSubset
  getOverlayStore: () => OverlayStoreSubset
  getAnalysisResultAdapter: () => AnalysisResultAdapterSubset
  getWorkbenchStore: () => WorkbenchStore
  getRuntimeStore: () => TrainingRuntimeStore
  getRepository: () => { loadTask(taskId: string): Promise<TrainingTask> }
  subscribeToSabakiStateChange: (cb: () => void) => () => void
  subscribeToWorkbenchStore: (cb: () => void) => () => void
  subscribeToRuntimeStore: (cb: () => void) => () => void
  subscribeToAnalysisUpdates: (cb: () => void) => () => void
}
```

### API

```ts
type GobanDataAdapter = {
  getSnapshot(): GobanPropsInput
  subscribe(callback: () => void): () => void
  destroy(): void
}
```

### Behavior

- `getSnapshot()`: synchronously reads from injected deps, aggregates into GobanPropsInput
- `subscribe(callback)`: registers callback; fires when any subscription source triggers
- `destroy()`: cleans up all internal subscriptions
- Never writes to any store
- Never calls any service method
- Never imports sabaki.js directly

### boardState aggregation

- When workbenchMode is 'analysis' and editWorkspace exists: read editWorkspace snapshot
- When workbenchMode is 'play'/'problem'/'recall': read documentStore.getCurrentTree/Position/Board

### overlayState aggregation

- paintMap, markerMap, dimmedStones from sabaki.state overlay fields or overlayStore
- analysis from analysisResultAdapter.getAnalysisForPosition(treePosition)

### settings aggregation

- Read from getSabakiState(); use defaults when null

### Task data loading

- Load task via repository.loadTask(taskId) when activeTab.taskId changes
- Cache per tab; invalidate on tab switch
- getSnapshot() returns cached task data (or null if not yet loaded)

## 7. boardInteractionController Specification

**File:** `src/modules/training/workbench/boardInteractionController.ts`

### Dependencies (injected)

```ts
type BoardInteractionControllerDeps = {
  getPlayServices: () => {
    documentStore: { playMove(vertex, options?): Promise<unknown> }
  }
  getRecallServiceOrStore: () => {
    submitRecallMove(input: { recallSessionId; userMove }): Promise<unknown>
  } | {
    submitRecallAnswer(vertex): { handled; changed }
  }
  getEditWorkspaceContext: () => ScratchEditExecutionContext | null
  getEditWorkspaceDeps: () => { invalidateEditAnalysis?(); scheduleEditWorkspaceAnalysis?() }
  getLegacySabaki: () => { clickVertex(vertex, options?): void }
  getIsMac: () => boolean
}
```

### API

```ts
type BoardInteractionController = {
  handleBoardClick(input: {
    vertex: [number, number]
    event: { button; ctrlKey; metaKey }
    activeTab: WorkbenchTab
    settings: { selectedTool; [key: string]: unknown }
    board: { get(vertex); markers }
    editWorkspacePresent: boolean
    task: { problemArea? } | null
    runtimeState: { activeCheckpointId?; correctionDraft? }
  }): Promise<void>
}
```

### Behavior

1. Build ResolverInput from input
2. Call resolveBoardInteraction(resolverInput) -> BoardInteractionResult
3. Route by mutationContract to appropriate executor
4. Never imports stores or services directly
5. Never writes to stores (executors write; controller only routes)

## 8. Container Rewrite

### Remove (from TrainingWorkbenchContainer.js)

- Lines 161-172: hardcoded gobanSettings
- Lines 174-191: projectGobanProps call with hardcoded boardState/overlayState
- Lines 195-222: original onVertexClick with manual resolver context assembly

### Add

- componentDidMount: create gobanDataAdapter, subscribe(this.forceUpdate)
- render: gobanDataAdapter.getSnapshot() -> projectGobanProps(snapshot)
- onVertexClick: delegate to boardInteractionController.handleBoardClick(...)
- componentWillUnmount: gobanDataAdapter.destroy()

### Preserve

- projectFromRuntime / projectFromWorkbench (shell/panel props projection)
- Shell handlers (handleModeChange, handleSubmit, etc.)
- Legacy handlers
- Store subscriptions (runtimeStore, workbenchStore)

### Container MUST NOT

- Read sabaki.state directly for board/overlay/settings data
- Call sabaki.clickVertex directly
- Call workbenchStore.updateTab directly
- Assemble GobanPropsInput (adapter does this)
- Branch on origin.provider

## 13. Prohibited Side Effects

1. Container reads sabaki.state directly for board/overlay/settings
2. Container writes workbenchStore or runtimeStore directly
3. gobanDataAdapter writes to any store or calls any service
4. boardInteractionController writes to stores (executors write)
5. Recall answer writes to game tree
6. Analysis scratch edits write to Attempt.userLine
7. Workbench click path calls sabaki.clickVertex (except deferred migration seam)
8. Container branches on origin.provider
9. gobanDataAdapter becomes a monolith of all app state
10. Container assembles GobanPropsInput

## 14. Out of Scope

- AI auto-move chain (aiMoveService)
- Full overlay pipeline WorkbenchMode wiring
- Problem area visual indicator
- Analysis mode full scratch workspace creation/teardown
- Board toolbar wiring
- Review queue wiring
- Left panel controls wiring
- TrainingRepository full CRUD
